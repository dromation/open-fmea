## Gap found and fixed: the Process Flow panel

`Codex_Instruction_ProductProcessCharacteristic_Linking_Slice.md` Section 6 specified a concrete, mockup-grounded GUI panel: a `Process`'s `Operation`s shown as an ordered step list, with the selected operation's `ProcessCharacteristic`s and its reachable `ProductCharacteristic`s (via `CauseInfluence`) shown in two tables — explicitly *without* Type/Criticality columns, since those require the not-yet-approved `ClassificationScheme`. `OpenFMEA_DNA_CoreReference.md` Section 10 treated this as "now a concrete part of that already-approved slice." It was not built. Grepping the entire tree for `process_flow`, `processes/<stable_id>/flow`, and "Linked Product Characteristics" returned nothing before this session.

Since this was already-approved scope with nothing new to decide, it was implemented directly rather than escalated back to an instruction-writing round:

- `fmea_app.views.process_flow` + `GET /processes/<stable_id>/flow/`, reusing the existing `_category_by_id`/`_label_for_reference` helpers and the same view-model shape as `process_characteristic_detail`.
- `templates/fmea_app/process_flow.html`: an ordered step list (plain CSS, no new JS/diagram library, per the instruction's tooling constraint), a generic key/value rendering of each `ProcessCharacteristic`'s `attributes` dict (no hardcoded key assumptions), and a Linked Product Characteristics table using the existing `_status_badge.html` component — confirmed no "Type" or "Criticality" column/label anywhere in the response.
- Reachable from three places already in the GUI: a new "Processes" panel on the FMEA detail page, a "View in Process Flow" button on the process-characteristic detail page, and a per-row link on the process-characteristic list page. No sidebar entry was added — `test_gui_navigation_scope.py`'s allow-list was deliberately left untouched.
- One demo `CauseInfluence` (`ProcessCharacteristic` "Seal installation force" → `ProductCharacteristic` "Seal seat surface condition") added to `seed_demo` so the panel has real content, matching the existing seed's demonstration intent.
- `tests/test_process_flow_view.py` (3 new tests, all passing): selecting an operation shows exactly its own process characteristics and not another operation's; the linked-product-characteristics table shows only characteristics actually reachable via `CauseInfluence` from that operation; the response contains no "Type"/"Criticality" column or label.

A small CSS addition (`.process-steps`/`.process-step`/`.attribute-table`) was made to `theme.css`, using only existing design tokens (`--accent-primary-strong`, `--bg-card-strong`, etc.) — no new visual language, consistent with the GUI-shell slice's own constraint.

## Findings (operational risk, not a code defect)

**1. (Recurring, confirmed again) `.git/index.lock` in `open_fmea` is present.** Previously flagged in at least two prior review rounds and still not root-caused. Confirmed again this session: a stale, several-days-old, zero-byte lock file. `git status`/`git diff` work; `git add`/`git commit` would not until it's removed. Recommend the user remove it locally on the Windows machine (native filesystem, unambiguous whether a git process is genuinely running) rather than from a remote/bridged shell.

**2. (New this session, likely the same root cause) `db.sqlite3` could not be opened from a remote shell reaching the repository over the device bridge.** Running `manage.py seed_demo` against the real database (not the test database — the test suite uses Django's default in-memory SQLite for tests and was unaffected) failed with `sqlite3.OperationalError: disk I/O error`, leaving a 271 KB `db.sqlite3-journal` hot-journal file behind; subsequent read attempts failed with `attempt to write a readonly database`. This points to the bridged filesystem not supporting the POSIX file-locking that SQLite (and, separately, git) need for safe writes — plausibly the same underlying cause as Finding 1. The database file itself is very likely not corrupted (a hot journal is SQLite's normal crash-recovery mechanism, not damage in itself); opening it once locally on the Windows machine should let SQLite roll the journal back automatically. **Recommend the user open the app locally (not through the remote bridge) before trusting `db.sqlite3`'s current contents, and avoid further writes to it from a bridged/remote shell.**
