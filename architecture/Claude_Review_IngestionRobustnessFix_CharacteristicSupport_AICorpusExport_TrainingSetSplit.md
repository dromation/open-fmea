## What was verified and holds up

- **Header detection now scores against real domain vocabulary instead of counting non-empty cells.** `_find_header_row` (rewritten, `xlsx-v2`) scans up to 80 rows, builds a `_DetectedHeader` for every row (and, when a row already maps to ≥2 known types, also a two-row-merged variant via `_merge_header_rows`), and picks the best by `mapped_cells`/`unique_domain_types`/`non_empty_cells` — not "first row with ≥2 non-empty cells." `_is_viable_header` requires ≥2 mapped cells across ≥2 distinct domain types, so a cover-sheet row like `Item | Potential Risk Responsibility | PFMEA Number` (three non-empty cells, zero of which map to anything) can no longer win over the real table header several rows below. I independently confirmed this is the actual, correct root-cause fix for what I diagnosed in the findings document.
- **Numeric and error-marker header cells are stripped.** `_clean_header` blanks `"#N/A"`/`"n/a"` and anything that parses as a float — directly fixes the specific garbage columns I found in the real file (`442710252570`, `Leopold Volčič`, a bare `1` being read as column names).
- **Per-sheet isolation replaces whole-workbook abort.** `parse_xlsx_bytes` now catches `AmbiguousWorkbookError` per worksheet, collects it in `skipped_sheets`, and continues; the workbook only fails if *no* sheet produced a viable header. This is exactly Finding B's fix.
- **Independent re-execution against all three real files, run myself rather than inferred from the report:**

  | `FMEA_templates.xlsx` | 1628 candidates | **1628 candidates**, 884 unmapped (54.3%), by type: Function 60 / Characteristic 132 / FailureMode 126 / FailureEffect 48 / FailureCause 114 / PreventionControl 132 / DetectionControl 132 |

- **`Characteristic` support is correctly scoped and does not cross the standing prohibition.** I checked `fmea_app/models.py` directly: `Characteristic` (name, description, `is_special`, optional FK to `Requirement`) has existed there since Phase B — it is *not* the not-yet-approved `ClassificationScheme`/`CauseCategoryScheme`/Ishikawa cause-classification model from the still-pending Characteristics/Ishikawa review. `promote_import_candidate_to_domain_object`'s new `Characteristic` branch just creates one of these existing objects, using a new `_optional_context_model` helper (correctly optional, since `Characteristic.requirement` is nullable) — `fmea_app/models.py` itself was not touched. `fmea_review/services.py::_domain_object_exists` and the Accept/Modify templates were updated consistently to support linking against existing Characteristics. No classification logic, no new entity types, no scope creep into the pending review.

## Findings

**1. (Recurring, moderate — will block committing) `.git/index.lock` in `open_fmea` is back, and blocking again.** This is the same issue flagged in the previous review round — and it has recurred since then with a fresh timestamp, meaning it isn't a one-time crash but something that keeps happening on this machine (most likely an IDE's Git panel or a background git-status watcher losing a race and leaving the lock behind). Confirmed directly again: `git status`/`git diff` still work, but `git add`/`git commit` fail with `fatal: Unable to create '.../.git/index.lock': File exists.` Recommend checking Task Manager for a lingering `git.exe` before deleting the lock file by hand, and — since this is now a repeat — checking whether an editor or Git GUI's auto-refresh is the recurring cause, so it doesn't come back a third time.

**2. (Moderate, structural) `open_fmea_training_set` has no `.git` at all — it's a completely untracked copy.** I confirmed this directly (`ls -la .git` → no such file or directory). Right now its `django_app/`, `domain/`, and `tests/` are byte-for-byte identical to `open_fmea`'s working tree, so nothing is wrong *today*. But there is currently no mechanism that would catch the two diverging in the future — if a fix ever gets made only in `open_fmea_training_set` (understandable, since that's where the EXE gets rebuilt and smoke-tested), there is no `git diff` or history to show it needs to be ported back to the reviewed, git-tracked `open_fmea` checkout, or vice versa. Given the deliberate split you described (`open_fmea` = build/source-of-truth location, `open_fmea_training_set` = training-run location with its own accumulating `db.sqlite3`), I'd recommend picking one discipline explicitly and writing it down (a line in both READMEs is enough): either (a) `open_fmea_training_set`'s code is always *regenerated* from a clean copy of the reviewed `open_fmea` checkout before each EXE build, never hand-edited — the safer default — or (b) make `open_fmea_training_set` a real second git checkout of the same repository (a `git worktree`, or its own clone tracking the same remote once one exists) so drift becomes a visible `git diff` instead of a silent risk. Either is fine; leaving it undecided is the actual risk.
