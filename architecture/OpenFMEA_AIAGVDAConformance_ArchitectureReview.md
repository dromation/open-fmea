# Open-FMEA Architecture Review — Conformance Against the AIAG & VDA FMEA Handbook (1st Edition, 2019)

Status: **Review, 2026-09-12** — written in direct response to the user uploading the official AIAG & VDA FMEA Handbook (1st Ed., June 2019) and asking whether the application "works the same" as the standard, and whether an AI should run in the background checking this ongoing. This is a review only — a gap analysis to inform a decision, not an implementation instruction. Grounded directly in (a) the handbook itself, read section-by-section for this review, and (b) the real, current code — `django_app/fmea_evaluation/calculators.py`, `django_app/fmea_app/risk_matrix.py`, `django_app/fmea_app/models.py`, `django_app/fmea_app/management/commands/seed_demo.py` — plus the project's own prior architecture docs (`OpenFMEA_DNA_CoreReference.md`, `OpenFMEA_MockupReadinessTracker.md`, `OpenFMEA_ClassificationScheme_ArchitectureDecision.md`), not from memory of what FMEA "usually" looks like.

## 1. Direct answer to "does it work the same now?"

**No, not fully.** The application's record-keeping skeleton is a reasonable, real simplification of the standard's middle steps (Function → Requirement → Failure Mode → Effect/Cause → Prevention/Detection Controls → Risk Evaluation → Recommended Action), and that much genuinely lines up with the standard's intent. But the single most standard-defining artifact of the whole methodology — the actual Severity/Occurrence/Detection criteria tables and the actual Action Priority (AP) decision table — is **not implemented**; what exists today is an explicitly self-labeled placeholder. Several whole steps of the standard's structure (Structure Analysis, Function Analysis's specific artifacts, the Failure Chain/Network) have no representation at all — already known and cataloged internally, not a new finding. And one entire third of the handbook — **FMEA-MSR (Supplemental FMEA for Monitoring and System Response)** — has never been discussed in this project under any name, and is a different thing from the already-known-and-held "PM-FMEA" concept (Section 5 below explains this confusion in detail, since it is the most consequential single finding of this review).

## 2. What already lines up with the standard

- The core entity chain `Function`/`Requirement` → `FailureMode` → `FailureEffect`/`FailureCause` → `PreventionControl`/`DetectionControl` → `RiskEvaluation` → `RecommendedAction` is a real, workable simplification of the standard's Steps 3-6 (Function Analysis → Failure Analysis → Risk Analysis → Optimization). The standard's own "Failure Chain" (Failure Effect + Failure Mode + Failure Cause, per element) is conceptually present, just flattened to one level instead of the standard's cascading multi-level network (see Section 4).
- `RiskEvaluation.severity`/`.occurrence`/`.detection` (1-10 each) matches the standard's three-factor 1-10 scale shape.
- `PreventionControl`/`DetectionControl` exist as their own linked entities, matching the standard's Prevention Controls (PC) / Detection Controls (DC) concept (Steps 2.5.3/2.5.4 of the handbook) rather than folding them into free text.
- `RecommendedAction.status` and `RiskEvaluation` history already support re-evaluating after an action, which is the shape (not yet the full letter) of the standard's Optimization step 6.4 "Assessment of Action Effectiveness."
- `ClassificationScheme`/`ClassificationTerm` + `ProductCharacteristic.is_special` at least represents *a* characteristic-classification concept, which is the right general shape for the standard's Special Characteristics idea — though the specific terms and DFMEA/PFMEA split don't match (Section 5).
- Both `classic-rpn` and `aiag-vda-ap-poc` already exist as pluggable `EvaluationDefinition` methods (`fmea_evaluation/calculators.py`) — the plumbing for "more than one risk-scoring method" is real and already used by the Risk Matrix. This is valuable groundwork: fixing the gaps below is a matter of improving/replacing what plugs into this seam, not re-architecting it.

## 3. Concrete gap: Action Priority (AP) is an explicitly-labeled placeholder, not the real table

`fmea_evaluation/calculators.py`'s own docstring says it outright: *"The Action Priority implementation is a PoC variant. The rule table is explicit and replaceable so a licensed organization-specific matrix can be substituted without changing persistence or export shape."* The actual `_action_priority_band()` function is a small set of invented threshold rules (e.g. `if s >= 9 and (o >= 4 or d >= 7): return "high"`), not the handbook's real table.

The real AIAG & VDA Table AP (DFMEA and PFMEA share one table; FMEA-MSR has its own separate one) is an **explicit lookup table, not a formula** — it enumerates every band-combination of Severity (grouped 9-10 / 7-8 / 4-6 / 2-3 / 1), then within each Severity band, bands of Occurrence (8-10 / 6-7 / 4-5 / 2-3 / 1), then within each of those, bands of Detection (7-10 / 5-6 / 2-4 / 1), mapping each of the resulting cells to High/Medium/Low — the handbook states it "accounts for all 1000 possible combinations of S, O, and D." The current PoC only approximates the general shape (severity weighted first) but does not reproduce the real table's actual cell values, and there is no evidence anywhere in the codebase that the real table was ever transcribed.

## 4. Concrete gap: no Severity/Occurrence/Detection criteria text exists anywhere

`EvaluationDefinition.rating_scales` — the one field that could hold the standard's actual criteria wording per band — is seeded (`seed_demo.py`) as literally just `{"minimum": 1, "maximum": 10}` for each factor. `RiskEvaluation.severity`/`.occurrence`/`.detection` are bare `PositiveSmallIntegerField`s with no link to the actual band text. A user (or an auditor) entering "Severity = 9" today has no way to see, anywhere in the application, that the standard's actual criterion for that value is *"Noncompliance with regulations"* — they are simply typing a number 1-10 with no guidance. The real Table D1 (Severity), D2 (Occurrence), D3 (Detection) each have specific, real criteria text per band (extracted in full during this review — available on request) that nothing in the app surfaces today.

## 5. Concrete gap: the RPN-threshold approach the standard explicitly advises against is the app's effective default

The handbook is direct about this: *"The RPN and S x O methods are not included in this publication... a Risk Priority Number (RPN) threshold is not a recommended practice."* Yet `classic-rpn` (`classify_rpn`: RPN ≥ 200 → "high", ≥ 80 → "medium", else "low" — a straightforward RPN-threshold scheme) remains a fully supported `EvaluationDefinition` method, and `risk_matrix.normalize_method()` **falls back to `classic-rpn` for any missing or unrecognized method value** — meaning RPN-threshold classification is the application's effective default today, while the (currently placeholder) AP method is the alternate, non-default option. This is worth a deliberate decision either way — RPN isn't forbidden for internal use, but presenting it as the default when the standard specifically singles it out as not-recommended is a conformance point worth the user's explicit call.

## 6. Gap already known internally, restated against the standard's actual step names

`OpenFMEA_DNA_CoreReference.md` already catalogs (Tier D, "genuinely new, no backing at all") the absence of a Structure Tree, Interface Matrix, and Parameter Diagram. Reading the standard directly confirms and sharpens this: these map to specific, named handbook artifacts, not generic "nice to have" diagrams —

- **Structure Analysis (DFMEA Step 2, PFMEA Step 2)**: the standard's **Block/Boundary Diagram** and **Structure Tree** (a hierarchical hardware/process breakdown, "each element exists only once") — not built. PFMEA's equivalent (**Process Flow Diagram** with Storage/Operation/Test/Transport symbols, **Process Structure Tree**) — not built.
- **Function Analysis (Step 3)**: the standard's **Parameter Diagram (P-Diagram)** — Input/Output/Control Factors/Noise Factors, Ideal Function vs. actual behavior — not built. The standard's **Interface Analysis** (the handbook's real term — it never says "Interface Matrix", worth correcting in any future mockup/doc that uses that name) covering five interface types (Physical connection, Material exchange, Energy transfer, Data exchange, Human-Machine) — not built.
- **Failure Analysis (Step 4)**: the standard's **Failure Chain** (Failure Effect + Failure Mode + Failure Cause per element) is present in spirit but flattened; the standard's **Failure Network** — where "a Failure Cause at one level is a Failure Mode at the next lower level," cascading Vehicle → System → System Element → Component → Feature — has no structural counterpart. `FailureMode`/`FailureEffect`/`FailureCause` today are a single flat level per `FMEA`, not a linked cross-level chain. This may be an acceptable, deliberate simplification for a first product rather than a defect — flagging it as a scoping decision, not an error.

## 7. Gap: Special Characteristics don't match the standard's actual DFMEA/PFMEA split

The handbook (Appendix D1) defines Special Characteristics loosely and explicitly leaves the actual symbol/category set **organization- or customer-specific** — it gives *"critical, key, major, significant"* only as examples, not a mandated list. But it is specific about the **structure**: DFMEA carries an optional, advisory **"Filter Code"** column (*"the Filter Code column replaces the Classification column because Special Characteristics are not required to be shown in the DFMEA"*); PFMEA carries the authoritative **"Classification"** column, where the PFMEA team determines whether a characteristic is "sensitive to manufacturing/assembly variation" (Special) or not (Standard), which then flows into Control Plans and drawings.

Today's `ClassificationScheme`/`ClassificationTerm` seeds one flat scheme of exactly four terms — **Legal, Safety, Functional, Decorative** — applied uniformly via `ProductCharacteristic.primary_classification`, with no DFMEA-Filter-Code-vs-PFMEA-Classification distinction, no link to `ProcessCharacteristic` specifically, and no Control Plan concept anywhere in the app. The four seeded terms read as a general characteristic-*type* taxonomy, not the standard's manufacturing-*sensitivity* flag. Since the standard itself says the actual terms are org-specific, this isn't strictly "wrong" — but the underlying two-column (advisory-in-DFMEA vs. authoritative-in-PFMEA) structure the standard requires is genuinely absent, which is a structural gap, not just a labeling one.

## 8. The most important single finding: "PM-FMEA" (held) and "FMEA-MSR" (never discussed) are two different things

This project's own docs (`OpenFMEA_DNA_CoreReference.md`, `OpenFMEA_MockupReadinessTracker.md`) have, since 2026-09-01, held off building **"PM-FMEA"** — described consistently across every prior doc as a **Preventive Maintenance / Asset / Work-Order track** (`MaintenancePlan`/`WorkOrder`, PM Compliance, Overdue WO, "PM-FMEA Responsible" role) — i.e., maintenance-and-asset-reliability FMEA. That concept **does not exist anywhere in the AIAG & VDA Handbook** — the standard has no "Preventive Maintenance FMEA" chapter at all.

What the standard *does* have, as a full, dedicated ~30-page section (Handbook Section 4, its own 7 sub-steps 4.1-4.7) is **FMEA-MSR — Supplemental FMEA for Monitoring and System Response**: a functional-safety-adjacent analysis of whether the *system itself* (diagnostics, sensors) or the driver detects a fault during real customer operation and responds before a hazard occurs, with its own Frequency (F) rating (replacing Occurrence), Monitoring (M) rating (replacing Detection), a distinct three-way Failure Scenario model (Non-Hazardous / Hazardous / Mitigated), and its own Action Priority table.

**These are unrelated concepts that happen to sound similar.** FMEA-MSR has never been named, scoped, cataloged, or held in any prior document in this project — it is a genuine blind spot, separate from and in addition to the already-known PM-FMEA hold. Whether FMEA-MSR is worth building is a real open question for the user (it is the more safety-relevant of the two, and is a normal, expected part of a full AIAG-VDA-conformant toolchain), but it should not be assumed already covered by the PM-FMEA hold — it isn't.

## 9. On "should we build an AI that runs in the background checking this"

A background *checking* capability is a reasonable idea, but it is worth being precise about what kind of capability actually helps here, because most of what this review found is **not** something an AI needs to detect — it's a fixed, known set of facts (the real S/O/D/AP tables) that simply need to be correctly entered into the system once. Recommending, in priority order:

1. **First, and highest value: make the real tables real.** Transcribe the handbook's actual Severity/Occurrence/Detection criteria text and the actual Action Priority lookup table (DFMEA/PFMEA's shared table, and FMEA-MSR's separate one, if FMEA-MSR is approved) into `EvaluationDefinition.rating_scales`/a real `calculate_action_priority` implementation, replacing the current PoC. This is deterministic, rule-based work — not an AI problem — and it resolves Sections 3-4 outright.
2. **Second: a deterministic, rule-based conformance checker**, not a generative AI — e.g., a scheduled or on-demand check that flags: a `FailureMode` with no `RiskEvaluation` at all; a `RiskEvaluation` under `classic-rpn` where the standard's advised `aiag-vda-ap-poc`-successor method is available but unused; a `ProductCharacteristic`/`ProcessCharacteristic` with high real-world sensitivity signals but no classification set; a `RecommendedAction` left "Open" past its due date with no re-evaluation. Every one of these is a plain database query, not a judgment call — this is the kind of "AI working in the background" that is trustworthy, because it is checking known facts against known rules, not inferring anything.
3. **Only after 1 and 2 are real** would an actual AI/LLM-based reviewer add anything distinctive — e.g., reading free-text failure mode/cause/effect descriptions and suggesting whether a Severity rating looks inconsistent with its own description, or whether a described characteristic sounds "manufacturing-sensitive" and might warrant Special Characteristic marking. This is the only piece of the ask that is genuinely an AI problem rather than a data-completeness problem, and it should be scoped as its own architecture decision (with its own human-review-gate, matching this project's existing standing rule for Slice L/Q's not-yet-approved AI-suggestion capability) once 1 and 2 exist to check against.

Recommend **not** building item 3 yet, and treating items 1 and 2 as the concrete, approvable next work if the user wants to close these gaps.

## 11. Recommendation

**Not ready to claim conformance today.** The application is a real, working simplified FMEA tool, not a faithful implementation of the AIAG & VDA methodology's risk-analysis and structure/function-analysis machinery. None of the gaps found here require throwing away existing work — `fmea_evaluation`'s pluggable-method design already anticipated exactly this kind of replacement. The recommended next step is a decision from the user on which gaps to close and in what order (Section 9's priority list is a proposal, not a decision), followed by the project's normal architecture-decision-then-instruction process for whichever is chosen — starting with Section 9's item 1 (the real S/O/D/AP tables) as the highest-value, lowest-risk fix, since it corrects the two most concrete, checkable gaps (Sections 3 and 4) without requiring any new model or migration.
