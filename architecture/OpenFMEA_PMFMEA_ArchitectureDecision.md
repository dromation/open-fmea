# Architecture Decision — Mockup 3: Preventive FMEA (PM-FMEA), First Increment

**Status: decided and implemented, 2026-09-12.** The standing hold on Mockup 3 (in force since 2026-09-01, reconfirmed 2026-09-04, and restated in `OpenFMEA_MockupReadinessTracker.md` and `OpenFMEA_DNA_CoreReference.md`) is lifted by explicit user instruction on this date: "nadaljuj, tako da bodo vsi mockupi vključeni, velja" ("continue, so that all mockups are included, agreed"), with an explicit follow-up confirmation to lift the PM-FMEA hold specifically. This document records the scope actually built, following this project's standing pattern of deciding a real, grounded first increment before writing code — the same pattern used for Mockup 7 (System, Slice E), Mockup 8 (ProductCharacteristic register, Slice P), and the three-part AIAG & VDA conformance work.

## 1. Why a first increment, not the full mockup

`OpenFMEA_MockupSpecifications_GUIWireframeArchitecture.md` and `OpenFMEA_MockupGUICodingRequirements.md` both classify almost the entirety of Mockup 3 as **Tier D** — no backing entity exists anywhere for Asset, WorkOrder, MaintenancePlan, PM Compliance/Overdue-WO/Next-PM metrics, Baseline/History versioning for an FMEA, a Reviews-scheduling entity, or an Open-EQMS Maintenance cross-system link. Building the full mockup literally would mean inventing five to six new entities and a versioning subsystem in one pass with no prior review — exactly the situation the 2026-09-01 hold was written to prevent ("hold off on writing the PM-FMEA/Asset/Maintenance architecture review until the currently-approved slices actually ship... nothing from Mockups 3 or 4 is to be turned into an implementation instruction before that review exists and is approved").

Now that the hold is lifted, this document *is* that review, and it deliberately scopes a first increment the same way Slice E scoped "System" out of Mockup 7's much larger vision, and Slice P scoped a read-only register out of Mockup 8's real content: build the one real, groundable capability the mockup depends on — **Preventive FMEA existing as a working FMEA type with a physical Asset a failure mode can be evaluated against** — and defer everything that requires inventing a maintenance-management module.

## 2. What this increment adds

1. **`FMEA.FMEA_TYPE_CHOICES` gains `("preventive", "Preventive FMEA (PM-FMEA)")`.** Purely additive — every existing choice (design/process/product/software/system) is untouched, and the existing generic `create_fmea`/`FMEAForm` machinery makes it selectable with no further code (no new create page needed).
2. **New `Asset` model** (`fmea_app.models.Asset`, a `StableModel`): `name`, `asset_code`, `location`, `status` (Operational / Down / Under Maintenance), `notes`. A plain physical-equipment identifier, mirroring the existing `System` model's shape and its `system_list`/`system_create`/`system_detail`/`system_edit` view/template pattern exactly (new standalone master-data pages: `asset_list`, `asset_create`, `asset_detail`, `asset_edit`).
3. **`FailureMode.asset`** — a new nullable FK to `Asset` (`on_delete=SET_NULL`), optional on every FMEA type, not just `preventive` (consistent with this project's pattern of not gating an optional field by type — e.g. `RiskEvaluation.failure_scenario` from the FMEA-MSR work is likewise present-but-optional regardless of context).
4. **New `pmfmea_worksheet` view/route/template** (`/pmfmea/`), mirroring the existing `dfmea_worksheet`/`pfmea_worksheet` pattern exactly: a read-only cross-FMEA worksheet filtered to `fmea_type="preventive"`, with one PM-FMEA-specific addition — an "Asset / Machine" column, matching the mockup's "Top High Risk Maintenance Items" table's Item→Asset/Machine join.
5. **`dfmea_worksheet` now also excludes `fmea_type="preventive"`** (previously `exclude(fmea_type="process")`, now `exclude(fmea_type__in=["process", "preventive"])`) — a necessary correction now that a third category exists; no existing FMEA has `fmea_type="preventive"` today, so this changes no existing FMEA's classification, it only correctly scopes what "DFMEA" means going forward.
6. **Sidebar**: one new link "Preventive FMEA (PM-FMEA)" under the existing "FMEA ANALYSIS" group (after PFMEA), and one new "MAINTENANCE" nav group with a single link, "Assets & Equipment" — both exactly as the mockup and `OpenFMEAMockupGUICodingRequirements.md`'s own coding requirements for Mockup 3/4 proposed ("a new MAINTENANCE group... Assets & Equipment... each with an external-link icon" — here it is an internal link, since the Asset entity is now real and internal to this app, not an external Open-EQMS deep link).
7. **`fmea_detail.html`** (the per-FMEA worksheet): the "Add Failure Mode" form gains an optional "Asset (PM-FMEA)" field, and a failure mode's row shows its linked asset (if any) as a sub-line, the same visual treatment as the description sub-line — no new column, no colspan changes.
8. **Domain layer**: `fmea_domain.Asset` (a `NamedEntity` — `asset_code`, `location`, `status`, `notes`) and `FailureMode.asset_id: str | None`, mirroring the Django model exactly, following the same domain-entity-parity precedent as `ProcessCharacteristic.special_classification_id` from Part C of the AIAG & VDA work.
9. **`seed_demo.py`**: one demo `Asset` ("Injection Molding Machine 03" / `IMM-03`, matching the mockup's own example verbatim) and one demo Preventive FMEA with one failure mode ("Spindle bearing wear") linked to it — mirroring the mockup's own "Top High Risk Maintenance Items" example row.
10. **Django admin**: `Asset` registered with a `ModelAdmin`, mirroring `SystemAdmin`'s shape exactly.

One migration: `0016_asset_alter_fmea_fmea_type_failuremode_asset.py` (Create `Asset`; alter `FMEA.fmea_type` choices metadata; add `FailureMode.asset`).

## 3. Explicitly out of scope (Tier D, unchanged from the mockup specs)

Nothing below has any backing entity, and none of it was built in this increment:

- **WorkOrder / MaintenancePlan** and every derived metric that depends on them: PM Compliance %, Overdue WO count, Next PM date.
- **"Assets Covered" donut**, the maintenance-lifecycle Validation Trajectory (Concept→Design→Install→Commission→PV→Operation→Monitor) with its Maintenance Readiness/PM-FMEA Coverage bars, and the "Top High Risk Maintenance Items" ranked-table widget as its own dashboard card (the plain worksheet table with an Asset column, built here, is the read-only substitute for now).
- **Baseline / History** versioning for an FMEA (a save-a-version/compare-versions workflow) — no versioning/snapshot entity exists for `FMEA` anywhere in this codebase.
- **Reviews** sub-tab — no review-scheduling entity exists (same gap already flagged against Mockup 1's "Reviews Due" stat).
- **"Links (Open-EQMS)"**, **"FMEA Workspace Settings"**, and any other Open-EQMS cross-system reference or deep link.
- **Two-tier tab hierarchy** (top-level FMEA-type tabs + a second row of Overview/FMEA Team/Scope & Configuration/Links/Reviews/Baseline/History sub-tabs) as its own page shell — the existing `fmea_detail.html` worksheet page is reused as-is for `fmea_type="preventive"`, exactly as it already is for design/product/software/system.
- **The "Linked Asset for Step 30" / "Maintenance Status" sections of the Engineering Context drawer** (an `Operation`→`Asset` link, distinct from the `FailureMode`→`Asset` link built here) — a separate, not-yet-decided relationship; deferred to a future increment if wanted.
- Mockup 4 (Consolidated Home's PM-FMEA rollup, the Operations module, the Project Health panel) — unchanged, still cataloged-only per the existing 2026-09-01 decision; nothing in Mockup 4 depends on anything decided here in a way that would make it buildable now.

## 4. Why this is a safe, additive-only change

- No existing `fmea_type` value, field, page, or test's meaning changed. `dfmea_worksheet`'s query correction affects zero existing rows (no `fmea_type="preventive"` FMEA existed before this migration).
- `FailureMode.asset` is nullable with `on_delete=SET_NULL` — deleting an `Asset` never cascades into deleting a `FailureMode` or anything under it.
- Two pre-existing tests (`test_dashboard_view.py::test_response_excludes_out_of_scope_sections`, `test_risk_trajectory.py::test_pages_have_no_canvas_and_no_propagation_chain_content`) used the bare string `"PM-FMEA"` as a canary for "nothing about preventive maintenance has leaked into this page," written when PM-FMEA had zero backing. Now that "Preventive FMEA (PM-FMEA)" is a real, permanent sidebar label appearing on every page (the same way "DFMEA"/"PFMEA" already do), that canary is stale, not wrong-code: both tests were updated to check for `"Maintenance Readiness"` instead — a phrase specific to the still-unbuilt maintenance-dashboard vision (Section 3) — preserving exactly the scope guarantee those tests existed to enforce.
- `Asset` and `FailureMode.asset` are deliberately excluded from `fmea_importexport/ofef.py`'s `_ENTITY_TYPES` registry, matching the established precedent that standalone master-data models (`System`, `ClassificationScheme`, `ValidationTest`, `Change`, `CharacteristicLink`) are not automatically wired into OFEF import/export.

## 5. Tests

New file `tests/test_pmfmea_first_increment.py` (21 tests): `Asset` model defaults/`__str__`/domain round-trip; `FailureMode.asset` optionality across FMEA types, domain `asset_id` round-trip, and `SET_NULL` (not cascade) on Asset deletion; the new `preventive` choice coexisting with every pre-existing choice; the `pmfmea_worksheet` view's scoping (shows only `preventive` FMEAs, shows the linked asset) and `dfmea_worksheet`/`pfmea_worksheet`'s continued correct scoping; the four new `asset_*` standalone pages (list/create/detail/edit round trip); the `FailureModeForm`'s new optional `asset` field; `add_failure_mode` saving (and not requiring) an asset; the sidebar's two new links; and `fmea_detail`'s new form field and worksheet-row asset display.

284 → 305 tests, all passing. `makemigrations --check --dry-run`: no changes pending. Fresh `migrate` + `seed_demo` (run twice, confirming idempotency) both succeed end-to-end.
